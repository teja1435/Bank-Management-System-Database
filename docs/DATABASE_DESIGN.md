# Database design

## Purpose and scope

The design follows the supplied training report's Bank Management System concept: organize branches, customers, accounts, and transactions using relational tables, keys, SQL operations, and PostgreSQL. It expands the report's three-table example with branch and joint-holder entities, stricter constraints, and atomic money-movement routines.

## Entities and relationships

- **Branch** has many accounts.
- **Customer** and **Account** have a many-to-many relationship through **Account Holder**; this supports joint accounts.
- **Account** can appear as the source or destination of many **Bank Transaction** records.
- A deposit has a destination account; a withdrawal has a source account; a transfer has both.

## Integrity and transaction behavior

Primary/foreign keys preserve row identity and relationships. Unique constraints cover branch codes, account numbers, emails, and phone numbers. Checks restrict account type/status, positive transaction amounts, nonnegative balances, and valid transaction shapes. Money movement functions lock affected account rows and update balances together with the ledger row. A failed statement rolls back all of its changes.

## Assumptions and limits

- Currency is recorded as an ISO-style 3-character code; this learning demo does not perform foreign exchange.
- No overdraft or interest model is included; balances cannot become negative.
- Opening balances are initial sample state and are not represented as transactions.
- Identity values are generated by PostgreSQL.
- This is not a real banking system and does not provide a user interface, authentication, permissions, regulatory compliance, encryption, or production audit controls.

## Operation flow

1. Create the schema and tables.
2. Add customers, branches, accounts, and account-holder links.
3. Execute a deposit, withdrawal, or transfer function.
4. PostgreSQL locks the relevant account rows, validates status and funds, updates balances, and inserts the ledger record in the same statement.
5. Use views and queries to inspect account balances, customer-account associations, history, and summaries.
